#### 2.2 knowledge_list / knowledge_get 扩展建议(按性价比排序,全部有生态先例)

1. **knowledge_list 加过滤参数**(S):`status?`(degraded/notice/unsupported)、`domain?`、`query?`(站名/域名子串)、`limit?`——先例=memory 的 search_nodes(query, limit) 与 fetch 的 max_length/start_index;消灭「171 行全表」的默认 token 成本。
2. **第三只工具 `knowledge_search(query)`**(S-M):模糊查站名/域名/命令名/坑文本,返回站点摘要列表——先例=context7 的 resolve-library-id(query 参与排序)、memory 的 search_nodes;补齐「全量读/检索/按名取」三件套(官方 memory server 的标准读面形态)。callTool 里现为硬抛「未知工具」,新增只需扩 KNOWLEDGE_TOOLS+callTool 两处(mcp-selfhost.ts:81-94/140-158)。
3. **两工具附 outputSchema**(S):spec 明文 clients SHOULD validate;我们 structuredContent 已产出(site/uri/commandCount/pitfallCount/health),补 schema 是纯声明工作。
4. **knowledge_get 结果加 resource_link**(S):`opencli://sites/{site}/knowledge` 资源面已存在(knowledge.ts:139-141),按 spec resource_link 条款放进工具结果,让支持 resources 的客户端可订阅——把「第三分发面」的三个面(resources/tools/HTTP)缝起来。
5. **注解补全**(S):fetch server 先例,纯读工具补 `idempotentHint:true / openWorldHint:true`(spec 同时提醒 annotations 属不可信声明,仅作描述)。
6. **远期(0.1.4+ 评估)**:events/schedule/watch 状态的 MCP 只读暴露,按 playwright-mcp `--caps` 模式门控、默认不注册——firecrawl「keyless 只给 3 只」与 dsh-browser-cdp「动态解锁」共同证明默认面越小越好。
7. **描述语言**(可缓):现两只工具描述为中文;mcp 生态主流英文,若面向外部消费者(IDE 助手)扩,考虑中英双语 description——按目标用户群决定,非技术项。

### 1. Bark(iOS/self-host)——推荐 P1

**端点与形态**(来源:bark-server 官方文档 docs/API_V2.md,`gh api repos/Finb/bark-server/contents/docs/API_V2.md` 当场解码;官方教程 https://bark.day.app/tutorial.md curl 当场抓取,2026-11-12):
- **GET 形态(教程原文)**:URL 由 key/title/body 组成三段式:`/:key/:body`、`/:key/:title/:body`、`/:key/:title/:subtitle/:body`,query 附参数(`?group=分组&copy=复制`)。
- **POST 形态(V2 主推,API_V2.md 原文「users should use the new REST API」)**:`POST {server}/push` + `Content-Type: application/json`,**device_key 放请求体**;也支持 `POST /:key` + JSON 体(key 在路径)或 form-encoded(教程 POST 示例 `-d'body=推送内容&group=分组'`)。
- **参数全表(API_V2.md 逐字)**:`title`(可选)、`subtitle`、`body`、`device_key`(必填)、`device_keys`(数组,批量)、`level`(值=`'critical'/'active'/'timeSensitive'/'passive'`)、`volume`(critical 音量)、`badge`(int)、`call`(=`1` 持续响 30 秒)、`autoCopy`/`copy`、`sound`、`icon`(iOS15+)、`group`、`ciphertext`(加密密文)、`isArchive`(=`1`)、`ttl`(归档存活秒)、`url`(点击跳转)、`action`(=`none` 点击不动作)。
- **加密(官方教程 encryption.md 逐字,curl https://bark.day.app/encryption.md)**:自定义密钥在 App 内设置;发送时「把 Bark 请求参数转换成 json 格式的字符串…加密,最后把加密后的密文作为 ciphertext 参数发送」;官方示例=`openssl enc -aes-128-cbc -K $key -iv $iv`(key 16 字节,IV 可随机但须以 `iv` 参数传入,密文 base64 后 urlencode)→ **AES-128-CBC、iv 外传形态可直接照写**(其他算法档位的完整枚举待核:教程页只给了 aes-128-cbc 示例;App 设置页可选算法档位未抓到)。加密价值原文:「推送内容在传输过程中就不会被 Bark 服务器和苹果 APNs 服务器获取」。

### 2. ntfy(self-host topics)——推荐 P1

**端点与形态**(来源:docs.ntfy.sh/publish/ WebFetch 当场取证 + 官方仓库源文档 docs/publish.md,`gh api repos/binwiederhier/ntfy/contents/docs/publish.md` 当场解码 5001 行,2026-11-12):
- **HTTP PUT/POST 到 `https://ntfy.sh/<topic>`**,body=消息文本;GET 亦可(publish.md 有 GET 示例,适合 webhook 类)。Topic 名 `[-_A-Za-z0-9]`、≤64 字符。
- **Header 全名与别名(逐字)**:`X-Title`(别名 Title/ti/t)、`X-Priority`(Priority/prio/p)、`X-Tags`(Tags/tag/ta)、`X-Click`、`X-Attach`、`X-Filename`、`X-Actions`、`X-Delay`(别名 X-At/At/X-In/In)、`X-Markdown`(Markdown/md,值 true/1/yes 或 `Content-Type: text/markdown`)、`X-Icon`、`X-Template`。**优先级 1-5**:5=max/urgent、4=high、3=default、2=low、1=min。
- **JSON publishing(实现首选)**:`POST https://ntfy.sh`(根路径,无 topic 在 URL)+ `Content-Type: application/json`,体=`{topic, title, message, priority, tags, click, actions, icon, markdown, attach, filename, delay, email, template, timezone}`——**topic 进 body 不进 URL,是凭据面最优形态**。
- **认证(publish.md :4317-4319 逐字)**:`Authorization: Basic dGVzdHVzZXI6ZmFrcXBhc3N3b3Jk`(base64 user:pass)、`Authorization: Bearer tk_AgQdq7mVBoFD37zQVN29RhuMzNIz2`(access token,tk_ 前缀)、或 `?auth=QmFzaWMg…`(base64 化的 Basic,query 兜底)。
- **限额**:消息体 **4,096 字节**,超限自动转附件(docs.ntfy.sh/publish 原文);ntfy.sh 请求限流(config 页取证)=`visitor-request-limit-burst` 默认 **60**、`visitor-request-limit-replenish` 默认 **5s** 补一,超限 **HTTP 429 + Retry-After**,并带 `RateLimit`/`RateLimit-Policy` 草案头(自host 可调)。缓存默认 12h;附件 15MB/文件(ntfy.sh 配置)。
- **actions(消息内交互按钮,≤3 个)**:header 语法 `action=<type>, label=…, …`,类型 `view`(view,label,url[,clear])/`http`(可 method/headers.<h>/body,默认 **POST**)/`broadcast`/`copy`;JSON 形态同字段数组——远期可做「点通知触发我方 ctl」的交互入口(v1 不做)。

**安全面评估**:①**topic 即密码(publish.md :3 逐字:「**the topic is essentially a password**」)**——PUT/POST /<topic> 形态把密码放 URL path(中转/日志面);**实现首选 JSON publishing 到根路径**(topic 在 body)+ token 走 Authorization header(不进 URL);`?auth=` query 仅作 header 不可用时的兜底,不做默认;②错误回显纪律同 Bark(name 只取 host,不回显完整 URL——topic 在 path 时同样适用);③scrub 链:message(=我方 body)照常过 scrub;ntfy.sh 公网服信任面=ntfy.sh 运营方,隐私敏感场景文档建议自host(ntfy 官方 docker 支持);④#12042(宿主用户)自建 bark+nginx 实战帖同时证明:自host push 基建在这批用户中已普及,ntfy selfhost 接受面成立。

**接入形态建议**:`type:'ntfy'` 通道类;配置=server URL+topic+可选 token(或从 URL path 拆 topic);send=POST 根路径 JSON `{topic, title, message:body, priority:3, tags:['bell']}`;可选 `Authorization: Bearer tk_…` header;成功判定 HTTP 200。量级 ~80 行。

### 3. Telegram Bot API——推荐 P2(既有预设升级,非从零接入)

**基线修正(重要)**:我方 **Telegram 已是 webhook 平台预设**——src/channels.ts:19 `PlatformId` 含 `'telegram'`、:65-70 `buildPayload` telegram 分支(POST `{chat_id, text}`,chat_id 从 URL query `?chat=` 拆)、:84 `platformOk` telegram 分支(`j.ok!==true` 判失败)、platformOf :27 按 `api.telegram.org` 推断、面板下拉已有 Telegram 项(client.ts:1292-1298)。基线「我方通道仅 webhook/email/dsh(notify.ts:443)」在 **channel-type 层正确,但「Telegram 全新接入」的隐含量级不成立**——0.1.4 的工作是升级为第一类通道而非新写。

**官方规格**(来源:PaulSonOfLars/telegram-bot-api-spec api.json,gh api 当场抓取,「A simple JSON description of the telegram bot API which updates itself every day」,pushed 2026-11-09,版本 **Bot API 10.4 / November 9, 2026**;主站 core.telegram.org 本轮网络不可达,规格以该镜像+grammY 官网仓为准):
- **sendMessage 参数(逐字)**:`chat_id`(Integer or String)、`text`(**1-4096 characters after entities parsing**)、`parse_mode`(格式化选项,MarkdownV2/HTML)、`entities`、`link_preview_options`、`disable_notification`(静默)、`protect_content`、`message_thread_id`(forum topic)、`reply_parameters`、`reply_markup`、`business_connection_id` 等。
- **429 限流处理**:types.ResponseParameters.`retry_after` 原文=「In case of exceeding flood control, the number of seconds left to wait before the request can be repeated」——429 响应体 `{ok:false, error_code:429, description:"Too Many Requests…", parameters:{retry_after:N}}`,**正确做法=等 N 秒重试**(grammY 官网 site/docs/advanced/flood.md 原文引用 FAQ:「Wait for the specified number of seconds. Retry the request.」)。
- **限流数值(grammY flood.md 逐字引用官方 FAQ)**:单 chat ≤**1 msg/s**(「avoid sending more than one message per second」);批量广播 ~**30 msg/s**(「the API will not allow more than 30 messages per second or so」);同文档强调精确限额是弹性未知数,429 可发生在任何请求。我方场景=每 tick 每 task ≤1 条,远低于限额,**429 处理只需读 retry_after 做一次有界退避**(旁路纪律约束下:retry_after≤5s 才就地重试,否则如实返回失败并附 retry_after 数值文案)。
- **proxy(现场证据)**:本机 `curl https://api.telegram.org` → **HTTP 000,exit 35(SSL 连接失败)**(2026-11-12 实测)——CN 部署环境必须走代理;实现=环境变量 HTTPS_PROXY/HTTP_PROXY + undici ProxyAgent(undici 7.30.1 已是上游 CLI 依赖,我方无新增依赖;uptime-kuma webhook.js 同款思路:其源码内建 `getAxiosConfigWithProxy`)。**注意我方 daemon 常驻进程的 env 注入路径要实测**(代理改环境后 daemon 需重探,与自愈链交互待核)。
- **现有 preset 的差距清单(升级项)**:①无 429 retry_after 读取与退避(现单发,失败即返回);②无 proxy 支持;③无 parse_mode/markdown 选项(现纯文本);④chat_id 从 query 拆的形态可用但文档化不足。

**安全面评估**:①**token 必在 URL path**(`https://api.telegram.org/bot<token>/sendMessage`)——官方 API 设计不可规避;TLS 下网络面安全,但**代理与日志面**:HTTPS 代理(CONNECT)不看 URL,HTTP 代理会看 → 文档必须要求 https 代理;我方通道 name 只取 host(channels.ts 未回显 token,WebhookChannel 构造 notify.ts:44-47 同款),错误文案只带状态码不回显 URL;②scrub 链:照常覆盖(text 在 JSON body);③bot token 泄漏后果=任意发消息,文档建议 @BotFather revoke 即可轮换(低爆炸半径,相对 SMTP 授权码)。

- **判定**:钳制逻辑保持不动(合法且被宿主实证接受)。**审读修订注**:按本节自引条文,「server 收到不认识的版 **MUST** 400」而我方不读不验——这是 server 侧第二处未履行的 MUST(第一处=Origin 校验,§6),原文降为「可选 S 级补强」的理由=现知两类消费者(宿主 dsh-mcp-client、官方 SDK)均不会发送不认识的版本头,风险面为空——**是风险取舍,不是合规豁免**;全稿「唯一 MUST 缺口」表述已相应限定为「传输安全面(Security Warning 章)唯一」。可选 S 级补强=按 SDK 语义验头(收到不在支持列表的头→400,未带头→按 init 版)。

### 6. basic/transports(Streamable-HTTP,全章实抓)——**本轮最硬的三条 MUST 发现**
- **规范**:①「Servers **MUST** validate the Origin header on all incoming connections to prevent DNS rebinding attacks」;②本机运行 **SHOULD** 只绑 127.0.0.1;③**SHOULD** proper authentication;POST body 单条 MUST;通知/响应→202;GET 可回 SSE 或 **405**;session id MAY 签发,签发后 client MUST 回带,server MAY 404 作废,client DELETE 终结,server **MAY** 回 405(=我方 DELETE 405 规范明文允许);无 stateful 需求可不签 session id。
- **我方现状**(源码+探针):单端点 POST /mcp ✓;GET→405+Allow:POST(探针 ④)✓ 规范允许;DELETE→405(源码 ②分支)✓ 规范允许;stateless 不签 Mcp-Session-Id ✓(MAY 不签);127.0.0.1 绑定 ✓(:400);Bearer 门 ✓。**三条未做**:Origin 校验无(规范 MUST,虽然 Bearer 门使 DNS rebinding 实际无法绕过认证,但 MUST 就是 MUST);MCP-Protocol-Version 头不验(§5);401 无 `WWW-Authenticate` 头(探针 ①:`no-token: 401 | WWW-Authenticate: false`)。
- **判定**:JSON-only+stateless 是规范内的合法形态;补 Origin 检查(S,把传输安全章/Security Warning 的 MUST 缺口关掉;全稿 MUST 缺口共两处,另一处=lifecycle 章协议版本头 400,见 §5 修订注)、验协议版本头(S)、401 加 WWW-Authenticate(S,见 §二 SDK 同款)。

### 7. server/utilities/completion(全章实抓)
- **规范**:`completions` capability MUST 声明才支持;`completion/complete` + ref/resource_template;values ≤100;ref/resource 引用 URI。**判定**:IDE 补全场景才值,宿主三工具面无 UI 补全——**远期,0.1.4 不做**。

### 8. basic/authorization(全章实抓)
- **规范**:「Authorization is **OPTIONAL** for MCP implementations」;实现 OAuth 者 SHOULD 全套 OAuth 2.1(PKCE/RFC 8707 resource 参数/RFC 9728 protected resource metadata/401 时 `WWW-Authenticate` MUST 指 metadata);token MUST 走 Authorization 头、MUST NOT 进 query string。**我方静态 Bearer≠OAuth,不落入 OAuth MUST**;token 头传递/不入 query ✓。SDK bearerAuth 中间件的 401 带 `WWW-Authenticate: Bearer error="invalid_token", error_description=…`(RFC 6750,packages/server/src/server/middleware/bearerAuth.ts:107-121 实读)——补这个头是 S 级、语义中性(不冒充 OAuth,只是标准 challenge 形态)。
